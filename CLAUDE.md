# CLAUDE.md

Guidance for Claude Code (claude.ai/code) and human contributors working in this repo.

## What Fireflyer is

A Python library that turns a CSV into an HTML visualization in a few lines of code. The user imports `fireflyer as ff`, calls `ff.chart.table(...)`, `ff.chart.pie(...)`, `ff.chart.bar(...)`, `ff.chart.map(...)`, or `ff.chart.number(...)`, and gets HTML back. Dashboards compose charts from a single YAML file. Polars is an internal implementation detail — the user never touches it.

Core flow, kept deliberately flat:

```
CSV → Parquet (dataset) → LazyFrame → Chart → HTML → Browser
```

**Datasets are managed, named entities** (`datasets.py`/`storage.py`): a CSV is uploaded, converted to **Parquet**, and stored in an object store (local folder for dev/tests, **Garage/S3** for portal). A chart references a dataset **by name**, resolved two ways: a **managed** dataset in the store, or an **inline** one — CSV carried in the dashboard's own optional `datasets:` block (`inline_data.py`), converted to Parquet once and cached by content checksum in the temp dir. Inline shadows managed for the same name. Inline exists for prototyping without leaving the editor (and for the assistant to invent sample data on request); managed is still the home for real or large data. No file paths either way. `Dashboard.from_yaml(text, datasets=<DatasetStore>)` resolves names to `(uri, storage_options)`; charts read via lazy `scan_parquet` with projection + predicate pushdown (`scan.py`), so only what a chart needs is read. Standalone/tests may pass a Parquet path directly as `dataset`.

Charts are declarations, not stateful objects. Every render re-scans the Parquet, re-executes chart logic, and re-generates HTML. No caching.

**`architecture.md` is the authoritative spec** for the layout DSL, filter model, and rendering rules. Read it before changing dashboard or chart behavior. Per project preference, **ask before editing `architecture.md`** — it's a controlled spec doc.

## Repository layout

```
fireflyer/
├── chart/
│   ├── table/  pie/  bar/  map/  number/   # each: chart.py, chart.html, chart.css, icon.svg, spec.md
│   └── __init__.py                         # exposes table/pie/bar/map/number as ff.chart.*
├── dashboard.py                        # YAML dashboard: parse, validate, render
├── datasets.py                         # DatasetStore: versioned uploads -> Parquet; a YAML doc per dataset
├── column_map.py                       # a dataset's column mapping: names + types, as YAML
├── storage.py                          # ObjectStore seam: local folder | Garage/S3
├── scan.py                             # chart data source: lazy scan_parquet (name -> uri)
├── filters.py                          # one filter model (declared + crossfilter)
├── params.py                           # editor param widgets (Text/Choice/Column/Int/Bool/FilterList)
├── config_edit.py                      # edit-modal: build form, surgical YAML block replace
├── dashboard.html / skeleton.html / cell.html   # dashboard Jinja templates
├── dashboard.css                       # dashboard-level styling (injected into output)
└── web/                                # FastAPI app + browser editor (dev tool, not core)
    ├── app.py                          # routes: editor page, /execute, /dashboard, /datasets/*, /chart/config/*, /chat
    ├── editor.html                     # the editor page's markup (`__FF_*__` placeholders)
    ├── static/                         # editor chrome, served at /static: editor.css/.js, gallery.css/.js, nav/profile/login.css
    ├── assets.py                       # STATIC_DIR + <link>/<script> tags versioned by file mtime
    ├── portal.py                       # gallery: Dashboards + Datasets tabs, stores
    └── chat.py                         # AI assistant: Anthropic SDK + DSL system prompt
tests/                                  # snapshot-based; snapshots/ holds expected HTML
demo/dashboards/                        # the starter dashboard; compose maps it in as the `demo` path
tests/data/                             # test fixtures (orders.csv + orders.parquet)
architecture.md                         # authoritative spec
```

Each chart folder is the modularity boundary: `chart.py` computes data, `chart.html` (Jinja2, autoescaped) renders it, `chart.css` is injected once per chart, `icon.svg` (required — the chart's 16×16 `currentColor` glyph, exposed as the class's `ICON`; shown in the filter panel's source column and the editor's chart-type picker), `spec.md` is the source of truth for that chart's behavior. **When changing a chart, update its `spec.md` in the same change.**

**Adding or changing a chart type?** Follow [`fireflyer/chart/SKILL.md`](fireflyer/chart/SKILL.md) — the step-by-step guide to the folder layout, `type:` wiring, the light/dark theming pattern, tests, and definition of done. (The `chart` Claude Code skill points at this same file.)

## Running things

```bash
docker compose up --build     # editor at http://127.0.0.1:8000 (mounts source + files/, hot-reload)
# or locally:
pip install -e ".[test]"      # deps: polars, fastapi, uvicorn, jinja2, pyyaml, python-multipart
python -m fireflyer.web        # browser editor at http://127.0.0.1:8000
pytest                         # snapshot suite
UPDATE_SNAPSHOTS=1 pytest      # regenerate snapshots after an intentional render change
```

Docker: `Dockerfile` + `docker-compose.yml` run uvicorn bound to `0.0.0.0`; the local `python -m fireflyer.web` entrypoint stays on `127.0.0.1`. The compose service bind-mounts `./fireflyer` and `./files`, so edits hot-reload without a rebuild — rebuild (`--build`) only when `pyproject.toml` changes.

If the venv breaks after moving the repo (stale editable path), re-run `pip install -e ".[test]"`.

## Versioning

The version lives in `pyproject.toml` (`version = "X.Y.Z"`), mirrored by `CHANGELOG.md` and the `vX.Y.Z` git tag. **Every release commit must bump the version** — follow Semantic Versioning: patch for fixes, minor for new backward-compatible features, major for breaking changes (pre-1.0, a breaking change may still go in a minor). When bumping: update `pyproject.toml`, move the `[Unreleased]` notes under a new `## [X.Y.Z] - <date>` heading in `CHANGELOG.md`, and update the compare links at the bottom of the changelog.

## Testing approach

Snapshot-based. Each test pairs an input CSV + chart/dashboard definition with expected HTML in `tests/snapshots/<test_name>.html` (see `tests/conftest.py` for the `snapshot` fixture). The goal is to verify the **exact** generated HTML.

- A rendering change will fail the relevant snapshot. If the change is intentional, regenerate with `UPDATE_SNAPSHOTS=1` and **review the diff** before committing.
- `dashboard.css` is injected into every dashboard render, so editing it changes the dashboard snapshot even when markup is unchanged — that's expected.

## Rendering rules (enforced, not stylistic)

- **Server-rendered, htmx-only.** Chart output is HTML + inline SVG + CSS + htmx attributes. No Alpine/Stimulus/React/Vue and no hand-written JS in chart output. The only `<script>` a chart's host page loads is htmx.
- **Jinja2 templates, autoescaped** — never build chart HTML with f-strings. CSV values and params must not be able to inject HTML.
- **CSS is per-chart**, namespaced under a chart class (`.fireflyer-table`, `.fireflyer-pie`, …), read once at import and injected inline. No shared base stylesheet, no `@import`, no build step.
- The **web editor is exempt** from the no-JS rule: it's a dev tool, not core architecture. Vanilla JS lives in `web/static/editor.js` (the mode switch, drag-to-resize, chat, the edit modal; the filter builder's rows are the shared `web/static/filter-builder.js`, loaded before it) and the editor's CSS in `web/static/editor.css`, linked from `web/editor.html` — files, not Python strings, served from `/static` and read per request, so editing them needs no server restart (uvicorn's `--reload` watches only `.py`; a change to a Jinja template or other non-`.py` file loaded at import *does* need `docker restart`). Keep editor JS there — don't leak editor JS into chart or dashboard output. Editor-only markup (resize handles, the per-chart pencil button) is gated behind an `editing` flag so it never ships in `to_html()`.

## AI assistant (`web/chat.py`)

The editor's chat sends the current YAML + request + the **available datasets' schemas** (column name/type, **no data**) to Claude (`claude-sonnet-4-6`, via the official `anthropic` SDK). Claude replies in text and, when a change is wanted, calls an `update_dashboard` tool with the **complete** new YAML; `run_chat` validates it with `Dashboard.from_yaml` before returning, with a bounded repair loop. Notes:

- The key comes from `ANTHROPIC_API_KEY` (loaded from `.env` via `python-dotenv` at app startup), stays server-side, and gates the feature (`CHAT_ENABLED`). Tests fake the client — never call the live API in the suite.
- **Dataset context.** The `/chat` route passes `run_chat(..., datasets=_dataset_schemas(request))` — the request-scoped dataset store's `list()` reduced to `{name, columns:[{name,dtype}]}`, never row data — so the assistant builds charts/calcs from real columns and won't invent datasets/columns. `chat.py`'s `_datasets_block` formats it into the user turn (`name: type` per column); the system prompt's **Datasets** section covers both kinds: use only the listed *managed* datasets, and write an **inline** `datasets:` block when asked to mock up or demo something.
- **History.** The conversation is kept in `localStorage` per dashboard (`ff-chat:<dash id or path>`, `{at, turns}`) for **seven days** after its last message — `localStorage` has no expiry, so `editor.js` drops an older one on load (`CHAT_TTL_MS`); the ＋ (`#chat-new`) clears it.
- **UI.** The assistant is one of the editor's **modes** (`#ff-chat`, reusing the `.ff-docs` shell as an `.ff-panel` side panel over the dashboard, like the YAML/docs/calcs panels); pick it from the topbar mode switch, and Esc or ✕ returns to view.
- `chat.py` embeds a condensed DSL spec as the (prompt-cached) system prompt. **Keep it in sync** with `architecture.md` and the chart `spec.md` files when the layout or chart rules change.
- This is editor-only and not part of the library core — same status as the rest of `web/`.

## Chart params & edit modal (`params.py`, `config_edit.py`)

The editor renders a hover **toolbar** on every chart (edit + delete buttons, only while the YAML pane is open — gated by an `editing` flag threaded through `render_skeleton`/`render_cell`/the async routes). Edit opens a modal form mirroring the chart's YAML config with real widgets; delete shows an "are you sure?" confirm, then `config_edit.delete_chart` removes the chart's block and all its layout placements (dropping now-empty rows). See `architecture.md`, "Chart params & editor modal".

- **`params.py`** holds the shared widget classes (`TextParam`, `DatasetParam`, `ColumnParam`, `ChoiceParam`, `IntParam`, `BoolParam`, `FilterListParam`). Each `Param` knows how to `render` an autoescaped input, `parse` the submitted value, and emit `to_yaml`. Widgets live here, not in chart code, so every chart reuses them. The filter row's inputs (`filter_fields`) and parser (`parse_filters`) are module functions, shared by `FilterListParam` **and** the dashboard filter panel's **+** form (global quick filters — viewer state, see `architecture.md` → "Global quick filters" and "Filter state in the URL"); keep the two on the one implementation.
- **Each chart declares `PARAMS`** — a `list[Param]` class attribute, one per constructor field, in display order. The modal also shows a **chart-type dropdown** above the params; changing it re-fetches the form (`build_form(..., type_override=)`) so the fields match the new type, and saving can swap the type. This is why chart files are a bit bigger. A test (`tests/test_chart_params_match_constructor.py`) asserts `PARAMS` names == the dataclass fields, so they can't drift.
- **`config_edit.py`** builds the form (`build_form`) and applies a save (`apply_edit`) by **surgically replacing only that chart's YAML block** — siblings, comments, and formatting elsewhere stay byte-for-byte. Comments *inside* the edited block are regenerated (documented limitation). The whole doc is re-validated via `Dashboard.from_yaml` before returning.
- **Adding to the layout**: the editor's left gutter shows hover **"+" buttons**. The per-row one (`.fireflyer-add-cell`) adds a chart to that row (the add modal). The insert-strip one (`.fireflyer-add-row`) opens a small **menu — chart / header / separator**: chart uses the add modal (`build_add_form` → `/chart/config/create`), while header and separator insert directly via `config_edit.insert_layout_item` → `/chart/config/insert-item` (a header defaults to text "New header"). A header can be **renamed in place** — double-click it in edit mode (`config_edit.set_header_text` → `/chart/config/header`, located by header index). **Headers and separators also get the hover toolbar** (compact badge, top-right) with **move / edit / delete**, addressed by their **layout-item index** (not a chart id): move → `config_edit.move_layout_item` (`/chart/config/move-item`), delete → `config_edit.delete_layout_item` (`/chart/config/delete-item`, confirm dialog). Edit is **header-only** (opens the same inline rename) — a separator has **no edit button** (and its wrapper gets padding so the thin `<hr>` is hoverable; the badge is centred on the item's top edge). Header edit mirrors move mode's focus feel: the dashboard gets `.ff-focus-mode` (dims everything but the edited header, suppresses hover UI, hides add strips) and the same topbar cancel button shows — `currentHeaderFinish` lets the button (mousedown+`preventDefault` so it cancels instead of blur-saving) or Esc restore the original; Enter/blur saves. Their **move is between-rows only**: it skips `buildMoveZones` and reuses the lit add-row strips as the sole drop targets (`enterItemMove` also hides the two strips flanking the moved item, which would be no-op drops; the shared move state is `moveCid` for charts vs `moveItemIndex` for items, unified by `inMove()`). **Tabs** move two ways: a drop on a **tab-bar slot** (`.ff-tab-zone`, built by `addTabZones`, none beside the moved tab) swaps it there with all its rows — `config_edit.reorder_tab` → `/chart/config/tab-reorder`, so the first tab can move too; a drop on a between-row strip moves just its key line (`move_tab`, not offered for the first tab, whose rows would be orphaned). Charts are rearranged via a **move mode** (not native drag-and-drop): a chart's **move** button lights the chart, dims the rest, and turns off every other interaction (resize, edit, add, crossfilter). Every valid spot lights up as a **blue drop-zone box** — a client-built overlay of column zones (before/after each cell; geometry-derived so merged/spanning cells align) plus **add-row strips in every gap between layout items** (drop into a new row there — `data-before` is a **layout-item index** into the full rows+headers+separators list, so it works around headers and separators too, not just between rows). The hovered box goes solid as a placement preview. The zones follow the **8 move-mode rules documented in `architecture.md`** — the client build is in `buildMoveZones`: side zones on every chart's left/right edge (`move_placement` → `/chart/config/move`); **common borders dedup** to one drop (`dedupBorders` keeps the taller candidate, so a **merged** chart's full-height side wins → dropping there adopts the span); between-rows via the add-row strips/internal gaps (`move_to_new_row` → `/chart/config/new-row`); a single **merge-down** bar (`.ff-move-zone-span`) down the *moved* chart's centre into the row below — `config_edit.merge_down` → `/chart/config/merge-down` adds a bare occurrence so *that chart's own* span grows down one row (only the moved chart, only downward, only one per dashboard); and the moved chart gets **no side zones**, nor its shared borders — **except** a **merged** moved chart, whose shared borders stay as **per-row unmerge** zones (`srcMerged` gate); dropping one is a plain `move_placement` that lands it single-row in that row (span removed). `dedupBorders` never collapses a border involving a merged chart. `move_span` still exists (place a chart spanning a target's whole span + 1 below) and is tested, but the editor's merge gesture now uses `merge_down`. If moving a member out breaks a span, `_finalize` repairs it by collapsing the broken span into its fullest remaining row. Inserts use **width 1** (`:1`); the first row's sizes drive the layout. **Column resize** on a merge group posts to `config_edit.resize_columns` (route `/chart/config/resize-columns`): it recomputes each cell's width from the fine (union) columns it spans, so dragging a boundary updates every row those columns belong to — even from an inherited/lower row — and spanning cells stay bare. Esc/Cancel exits; an emptied source row is dropped. Move-mode clicks/mousedowns are captured (`stopPropagation`) so nothing else fires. `add_chart` generates a unique id, appends the chart block, and splices a placement into the `layout:` list (flow-style rows only). All gated by `editing`.
- **Every `Param` declares what it reads** (`reads`, one of `params.READS`: none / column / columns / calc / calcs / filters — required, the base class leaves it unset; `ListParam(reads=…)`). `params.columns_read(PARAMS, values, calcs)` turns a chart's values into the columns it reads (None = every column: a `columns` list left empty with no calcs), and **charts read data only through `scan.scan_chart(self)`**, which hands them just those columns — so an undeclared column fails at once. `Dashboard.uses(yaml)` / `columns_used` derive what a dashboard reads from the same declarations (column calcs traced to dataset columns via `CalcSet.dataset_columns`). `tests/test_chart_columns.py` holds every chart to it.
- **The uses index**: `(dataset, column)` pairs per dashboard (`""` = the dataset itself, `"*"` = every column), written on create/save, dropped on delete — `_SqlUses` (`dashboard_uses` table, both SQL stores; a pre-index dashboard is indexed on first read) and `PathDashboardStore.uses()` (`<FIREFLYER_DATA>/<path>/uses.json`, re-indexed by file mtime). The dashboards list's Datasets column, the datasets list's Dashboards column, the dataset page's per-column Dashboards column and the delete-guard all read it (`app._uses`).
- To add a widget type: implement a `Param` subclass in `params.py`, then reference it from a chart's `PARAMS`. Follow [`fireflyer/PARAM_SKILL.md`](fireflyer/PARAM_SKILL.md) — the guide to the `Param` contract, wiring a chart's `PARAMS`, the surgical save path, and the sync-guard test (the `param` Claude Code skill points at this same file). Pure logic lives in `params.py`/`config_edit.py` (not `app.py`) so it unit-tests without the web stack.

## Portal mode (`fireflyer/web/portal.py`, `fireflyer/portal.py`)

Opt-in, editor-only. An **owner-approved exception** to the "no persistence/multi-user" anti-goal, scoped to `web/` (same status as the AI assistant and `params.py`). It stores many dashboards in a database and lists them in a gallery, **reusing the existing editor unchanged**.

- **The editor is already stateless** — every `/chart/config/*`, `/execute`, `/dashboard` route takes YAML text in from the browser and returns new YAML; nothing is persisted server-side. Portal only wraps this with a persistence + listing layer, so no existing edit logic changes.
- **Enable it** with `FIREFLYER_PORTAL=1` (the `python -m fireflyer.portal` entrypoint sets it, reads `portal.yaml`, and binds `0.0.0.0`). Off by default: `/` is the usual single-dashboard editor. On: `/` is a **gallery** — a table (name, author, last updated) with per-row **Clone / Remove** (the name opens it in the editor) and a top **+ New dashboard** button; New and Clone each prompt for a name in a native `<dialog>` modal (the gallery carries a little vanilla JS, allowed as editor chrome). Routes, all **UUID**-addressed: `POST /new` creates a **blank** dashboard (`_empty_yaml`, valid but no datasets/charts/layout) with the modal name + author; `POST /d/{id}/clone` copies one under a new name (`_set_yaml_name` rewrites the `name:` line); `GET /d/{id}` opens the editor seeded with that row's YAML; `POST /d/{id}/save` validates + persists; `POST /d/{id}/delete` removes. The editor **topbar** has left/right groups filled via `editor.html` placeholders — the opened-dashboard editor **mirrors the dataset detail page**: a **back button**, no brand text. **left**: `__FF_NAV__` (`_BACK_HTML` = `portal_mod.back_button("/", …)` — the **shared** back button, same `.ff-back` style + SVG as the dataset detail's back; empty in plain-local mode; (**no** Dashboards|Datasets switch — that's for the list pages; a selected dashboard leads with just the back button, like the dataset detail) + `__FF_DASH_NAME__` (`_dash_name_html`) — the title: the name (`#ff-dash-name`) with the description's first line under it (`#ff-dash-sub`, ellipsized), together one button (`#ff-dash-head`) opening a **card** (`#ff-dash-about`) with a name field and a description field, two-way-bound to the YAML `name:`/`description:` keys (`yamlName`/`setYamlName`/`setYamlDescription`; the topbar follows as you type, clicking away or ⌘/Ctrl+Enter keeps, Esc reverts; in view mode the card is read-only and opens only when there's a description; edit `name:` in the YAML → title updates); `__FF_MODES__` (`_mode_switch()`, `#ff-modes`) — the **mode switch**, before the name; **right**: `__FF_PATHDD__` (`portal_mod.path_dropdown(...)` — the **path dropdown**, local paths mode only), `__FF_SAVE__`, `__FF_THEME__` (theme switch), `__FF_USER_MENU__` (profile). (No `__FF_BRAND__` — the Fireflyer logo/brand was removed from the editor topbar.) The **mode switch** is a 7-segment icon control — **view / edit / code / diff / chat / calcs / docs**, exactly one active, reusing the `.ff-theme` segmented styling. **view** is the default and the dashboard is full width in every mode; the other four (code/chat/docs/calcs) each open one `.ff-panel` **beside** the dashboard — a two-column grid, never an overlay, since every one of them is used *while* looking at the dashboard. The split is keyed off a single `panel-open` class (not per-mode rules) and the mode classes are derived from `MODES`, so adding a mode cannot leave a stale column behind. Panels have **no close button**: the switch is the only way in or out (Esc also returns to view). The panels are **direct children of `.layout`** — `grid-area` only places an element in its parent's grid, and while they were nested in `#output-pane` the split silently did nothing (`setMode` owns every show/hide, and clicking the active segment returns to view). **edit** opens no panel — it is for rearranging the dashboard, so nothing covers it — and is the only mode that shows the on-canvas affordances, CSS-gated via `.layout:not(.mode-edit)`; the server always renders the editor chrome, so switching modes costs no re-render (`editingDisabled()` is just `currentMode !== 'edit'`). The YAML `<textarea id="code">` is the **source every control reads and writes** (chart modals, calcs manager, chat, save); **`code`** mode shows it in a panel for hand-editing — through a **code editor** (`web/static/yaml-editor.js`: CodeMirror 6, browser ES modules **vendored** into `web/static/vendor/` by `scripts/vendor.py` — pinned versions, downloaded once and committed, **no npm, no build, no network**; htmx is vendored the same way. The **import map** in `editor.html` gives each package one URL, since two copies of `@codemirror/state` break CodeMirror. `tests/test_editor_page.py` guards that the editor loads nothing from another origin and that every vendored file's imports resolve through the map. To upgrade, change a version in `scripts/vendor.py`, run it, and paste the import map it prints). The editor **mirrors** the textarea rather than replacing it: an edit is written back with an `input` event; a write to `codeEl.value` is caught by a setter on the textarea and applied as the smallest change, so cursor and undo survive; `codeEl.focus()` focuses the editor and `codeEl.cmView` is the view. If the editor fails to load, the plain textarea stays and works. A top panel (`outline` in `yaml-editor.js`) shows a chip per top-level key that jumps to its line, lit for the cursor's section; a hop highlights the key's whole block (`blockEnd`). **Line links**: a line-number click (shift-click for a range) or an outline hop highlights lines (the `linked` StateField) and writes `?line=12` / `?line=12-20`; a link with it opens code mode there, and leaving code mode clears it. (Inside `yaml-editor.js`, `history` is CodeMirror's undo history — use `window.history`.) Modules follow the editor mode via `ffEditor.onModeChange(hook)`. `charts`, `calcs` (`dataset / calc`), a tabbed `layout` and `datasets` open a menu (tooltips: a chart's `title`, a calc's `name`) of charts (each with its type's `icon.svg`, sent in the `/yaml/assist` schema as `icons`) / tabs / inline datasets. It lints and completes through `POST /yaml/assist` → `fireflyer/yaml_assist.py` (`lint`: problems pinned to their token, chart errors in plain words; `schema`: chart keys and value kinds straight from each chart's `PARAMS`, datasets + columns, calcs). Editor-only, like the rest of `web/`. Since setting `.value` fires no `input` event, `run()`'s `finally` is what refreshes Save state and the editable title after a programmatic rewrite. The **docs** panel (`#ff-docs`) lists each chart type as a collapsible `<details>` with its `spec.md` rendered — a tiny in-house markdown→HTML (`_render_spec_md`: #/## headings, `-` bullets, `**bold**`, `` `code` ``); the docs are read + built once at import (`_build_chart_docs`/`_CHART_DOCS_HTML`, spliced via `__FF_DOCS__`). Esc or ✕ closes it. **Save** (`#ff-save`, a floppy-disk icon in the `.ff-savebar` group with Discard `#ff-discard`) is **hidden until there are unsaved changes** (`updateSaveState()` compares `codeEl.value` to `savedYaml`; distinct from preview-*stale*), saves on click or ⌘/Ctrl+S, and a `beforeunload` guard warns if you navigate away dirty. Unsaved edits are also kept in `localStorage` (`ff-draft:<dash id or path>`, `{yaml, base, at}`, written by `updateSaveState`/`keepDraft`) and restored on reopen with a toast. **Version history**: every save is a numbered version (`DashboardVersion`: version, unix `created_at`, author) — the portal stores' `dashboard_versions` table (`_SqlVersions`), or JSON files under `<FIREFLYER_DATA>/<path>/history/<stem>/` for `PathDashboardStore`; no-change saves are skipped, and a pre-history dashboard gets a baseline v1 on its next save. `GET /d/{id}/versions[/{n}]` serve them to the **compare** view — the **`diff` mode** (after code; no side panel — `MODES.diff` is `null` and `setMode` calls `window.ffEditor.onMode`, which `diff-view.js` sets to open/close the full-width `#ff-diff`; `web/static/diff-view.js`, `@codemirror/merge`), which talks to `editor.js` only through `window.ffEditor`. The sides ride in the URL as `?compare=v3..v5` (dropped when there are unsaved edits or no history, and on leaving the mode); a link with it opens compare mode on those versions. The **theme switch** (`_theme_switch`, `#theme-switch`) is a **3-segment icon control** — inline-SVG **A / sun / moon** for Auto / Light / Dark, no text labels (`title`/`aria-label` carry meaning; icons use `stroke=currentColor` so they follow the segment colour); it sits in the **topbar on every page** — the editor (`__FF_THEME__`) and every gallery page (`_shell`), in every mode — built by `portal.theme_switch()`, styled in `nav.css`; one choice for all pages (`localStorage` `ffTheme`, applied as `data-ff-theme` on `<html>` by `editor.js` / `gallery.js`, whose `gallery.css` palette honours it). Exactly one `#theme-switch` per page. There is **no Run button or status text**: instead the output pane (`#output-pane`, class `output`) shows a **↻ Refresh** overlay (`#refresh`, centered both axes, `clamp`-sized) that appears — over a greyed-out, stale preview — only after a **manual** YAML edit (`codeEl` `input` → `markStale()` adds `.stale`); `run()` re-renders and clears it. The stale preview is greyed **but stays interactive** (`.stale .pane-body` must *not* set `pointer-events: none` — that blocked the row/column resize handles; the resize/move handlers read the live textarea and re-render on release, so acting on a stale preview is consistent). Programmatic edits (chat, config-edit) call `run()` directly so never go stale. Rare config-edit error messages use a transient bottom toast (`#ff-toast`, `flash()`) instead of the old status line.
- **The dashboard name is the YAML's required top-level `name:` key** — part of the definition, not portal metadata, so local and portal mode share one format. `Dashboard.from_yaml` **requires** a non-empty `name` (parsed into `Dashboard.name`; missing/empty raises `DashboardError`). Name is a **DB column** but re-derived from the YAML on every `create(yaml, author)`/`save(id, yaml)`, so editing the `name:` key in the editor renames the listing; New/Clone write the modal name into the YAML. **`author`** is a separate column (the logged-in user via `_current_author`, set at create/clone, untouched by saves). `web/chat.py`'s DSL prompt teaches `name:` so the assistant emits it, and `architecture.md` documents it under "File shape" and the "Portal mode" section.
- **Dashboards are stored as an opaque YAML text blob**, validated by `Dashboard.from_yaml` on save — never decomposed into normalized tables (that would break the surgical-edit / comment-preservation design). Datasets are **not** in the YAML — charts reference them by name (`dataset: orders`) and they live in the dataset store (see the Datasets tab below), so a dashboard blob is self-contained layout only.
- **Two stores in `web/portal.py`**: stdlib **`SqliteStore`** (in-memory for tests, a local file for dev) and **`PostgresStore`** (runtime; imports `psycopg` lazily). `make_store(dsn)` picks by DSN. The driver is an optional **`.[portal]`** extra, so `pip install -e ".[test]"` and CI stay database-free. Store logic + the gallery HTML live in `portal.py` (not `app.py`) so they **unit-test without the web stack** — `tests/test_portal.py` uses in-memory sqlite and never touches a live DB (same rule as the chat tests).
- **Auth (`web/auth.py`)** — portal mode is gated behind a login; default **admin/admin** (`FIREFLYER_USER`/`FIREFLYER_PASSWORD`). Intentionally minimal, built on **two independent seams** so SSO/LDAP drop in without touching routes: (1) the `Authenticator` protocol — `verify(user, pass) -> identity | None`, default `PasswordAuthenticator`, swap via `app.state.authenticator`; (2) an HMAC-signed session cookie (`set_session`/`current_user`/`clear_session`, secret from `FIREFLYER_SECRET`), independent of *how* the identity was proven — an SSO callback just calls `set_session`. A middleware guard redirects anon requests to `/login`; routes are `GET/POST /login`, `POST /logout`. The **profile button** (`auth.user_menu(identity, extra="")`) is a native `<details>` dropdown (username → optional `extra` → **Log out**), styled by `web/static/profile.css` (linked from both the editor page and the gallery); it sits top-right in the gallery (`render_gallery(..., user_menu)`, no `extra`) and the editor (`__FF_USER_MENU__` slot). Auth is on iff portal is; local mode has no login. Pure functions in `auth.py`, unit-tested without the web stack (`tests/test_auth.py`). **The SSO/OAuth extension recipe is in `architecture.md` → "Portal mode → Authentication".**
- **Datasets tab (`fireflyer/datasets.py`, `fireflyer/storage.py`, gallery in `web/portal.py`)** — the gallery's list pages (the "overview") share `_shell` and lead with a **Dashboards | Datasets | Access segmented switch** (`nav_switch`, `.ff-switch`) on the **left**; in local paths mode a **path dropdown** (`path_dropdown`, `.ff-pathdd` — a labelled `<details>` showing the active path, menu right-aligned; picking one hits `/path/{name}`) sits on the **right** of the topbar. Both are pure functions whose CSS is the shared `web/static/nav.css`, linked from both the gallery `_shell` and the editor page. A **selected dataset** is a **detail** page (`_shell(..., detail=True)`): `_shell`'s own left-nav is suppressed and the topbar lead is built in `topbar_left` — `back_button` + the name block (a `.topbar-lead` flex row), **no switch**; the path dropdown still rides on the right (from `_shell`, local paths mode). So the two **selected-item** pages (dataset detail + dashboard editor) match — **back + name on the left, path dropdown on the right, no switch** — while the switch lives only on the two **list** pages. Portal/plain-local detail stays **back-only** (no `paths` → no dropdown). A `DatasetStore` (over an `ObjectStore`: local folder for dev/tests, **Garage/S3** at portal runtime, chosen by `FIREFLYER_S3_ENDPOINT` env) holds each dataset as **versioned files** — every upload's original (`datasets/<name>/raw/<major>.csv`, a **major**) and the **latest** computed Parquet (`datasets/<name>/data.parquet`) — keyed by a **unique name** (no id), plus **one YAML document** per dataset (details, versions, each version's **column mapping** — with its `permissions:`), kept by a catalog: `ObjectCatalog` (a `dataset.yaml` beside the files — local mode, the default) or `SqlCatalog` (a `datasets` table in the portal DB). The **column mapping** (`column_map.py`) lists the dataset's columns, each `name: {formula: …}` — a formula over the uploaded columns in the calc grammar (`+ - * /`, `str2dt()`, and `to_number()`, which reads text as a number; Int64 when every value is whole). There's no type field: a column's type is what its formula gives, read from the built data and shown in view mode with its first 5 distinct values (`DatasetStore.examples`, from the built Parquet). Edit mode is a name + formula per column (✕ drops, ＋ adds); a rename is the same formula under a new key (`column_map.renames`); a column marked `service: true` (`Rule.service`, the crossed-out-eye toggle) is built and kept in the version's schema but **dropped from `data.parquet`** and from `Dataset.columns` (it's in `Dataset.service`), so no chart, editor picker or the assistant ever sees it; the **minor** counts mapping changes — one counter per dataset, never reset (`datasets._next_minor`): a new upload is the next **major** and keeps the minor unless the mapping it carries forward changed (1.3 → 2.3, or 2.4 with new columns), a saved mapping is the next minor; compare lists one entry per minor (`#3`). `create`/`replace`/`remap` with `build=False` queue a version and the app runs `DatasetStore.build` in the background (`_build` in `app.py`, FastAPI `BackgroundTasks`); a value that won't cast fails the build and keeps the previous version (`error` on the dataset). Renamed columns cascade into dashboards via `dashboard.rename_column_refs` (only column positions: `x`/`y`/`column`/`lat`/`lng`, `columns`/`sort`, filters, that dataset's calcs). The detail page's columns switch **view / edit / code / compare / access** (`web/static/dataset-columns.js`, which loads CodeMirror through the same import map as the editor — `assets.import_map`, from `static/vendor/importmap.json` — and shares `yaml-look.js` + `code.css`); the version chip opens the history (`_history_menu`: compare, delete an upload not in use). Unversioned datasets (`<name>.parquet` + `<name>.yaml`) migrate to 1.0 on first load, guessed types kept. Routes (`app.py`): `GET/POST /datasets` (list + multipart upload → CSV-to-Parquet), `GET /datasets/{name}` (detail: its columns — view/edit/code/compare/access — with example values; no data preview), `POST .../replace|rename|delete`. **Delete-guard** (409 if a dashboard still references it) and **cascade-rename** (rewrites `dataset:` refs across dashboards) use `Dashboard.dataset_names()` + `dashboard.rename_dataset_ref()`. Store logic + gallery HTML are pure functions, unit-tested without the web stack (`tests/test_datasets.py`, `tests/test_portal.py`); the S3/Garage read path is wired but validated only with Docker.
- **Access tab** — the list pages' switch is **Dashboards | Datasets | Access**, on every list page in every mode. Opened on first use (`app._role_store()`), so importing the app creates no file; tests set `app.state.roles`. Names are trimmed and unique (`RoleError` → 400). `render_access` in `portal.py`, tested in `tests/test_access.py`.
- **Dataset permissions + view as a role** — the dataset page's mode switch has a fifth mode, **access** (`_COLUMN_MODES`): only the roles that **may** read the dataset are listed, under **Role | Filters | Rows** headers (Rows: how many rows the role sees — `DatasetStore.rows_seen`, recounted on change via `POST /datasets/{name}/access/rows`; — when a filter names a missing column); a role's filters read as a chart's filter panel lists them — a compact row each (`portal.access_filter_row`: type, column, op, values, ✎ edit / ✕ remove; its parts ride as hidden `filter_*` inputs for the save) — over a **draft row**, the chart builder's own fields (`params.filter_fields` with `config_edit.dataset_context(name, resolve)`, driven by the shared `web/static/filter-builder.js` — the same script the chart modal and calcs manager use; a page sets `ffFilterBuilder.context(row)` → `{yaml_text, filter_dataset}`) where ✓ adds the filter (`POST /datasets/{name}/access/filter` → its compact row) or replaces the one being edited; the draft is left out of the save. No filters = **Full**, the draft's column picker's first entry (added by `dataset-columns.js` from `ds-full-tpl`, accent and ruled off; picking it drops every filter). - **Local paths mode (`fireflyer/web/paths.py`)** — the *non-portal* way to manage many dashboards + datasets against your own filesystem, without a DB or login. Enable it by setting **`FIREFLYER_PATHS`** to a base dir inside the container; **each host folder you Docker-map under that base is a switchable "path"** via the topbar **path dropdown** (right side). There's **no in-app path management** by design — you add/remove/repoint a path by editing the compose volume mappings and restarting. Off (unset) → `/` stays the single-dashboard editor; on → `/` and `/datasets` become the same gallery/editor pages as portal, minus auth. A path's **dashboards are `<path>/dashboards/*.yaml`** (files you own/commit) via `PathDashboardStore`, which mirrors the portal store surface (`list/get/create/save/delete` over `DashboardRow`) so **every route is store-agnostic** — the dashboard **id is its filename stem** (slugged from `name:`, path-traversal guarded). Its **datasets are an isolated blob store per path** at `<FIREFLYER_DATA>/<path>/` (Parquet you upload via the web, never written into your dashboard folder). The **`demo` path is the repo's `demo/` folder**, mapped in by docker-compose (`./demo:/paths/demo`) rather than seeded — what you open in the browser is the file in git, and it carries its own data in an inline `datasets:` block. `DEFAULT_YAML` is read from that same file at import, so the app's starter and the demo path cannot drift. Portal mode is unchanged (`app.state.store` set → those helpers return the DB/singleton). `paths.py` logic is unit-tested without the web stack (`tests/test_paths.py`).

## Non-negotiable constraints (from architecture.md)

Explicit anti-goals. Do not add them, even if they seem like good engineering:

- **No abstractions for future flexibility.** No service layers, repositories, registries, plugin frameworks, or DI containers until actually needed. The dashboard's `type → class` lookup is a plain dict — keep it that way. (One **deliberate, owner-approved exception**: the `params.py` widget layer, which exists to power the editor's edit modal. It earns its keep — don't take it as license for more abstractions.)
- **No frontend tooling.** No npm, webpack, vite, tailwind, or bootstrap. PicoCSS-compatible markup and inline SVG only.
- **No production concerns.** No auth, multi-user, caching, streaming, large-dataset optimization, or realtime updates. (One **owner-approved exception**: **portal mode** — see below — adds DB persistence + a dashboard listing, scoped to `web/`. It does *not* license auth, caching, or the rest.)
- **No chart features beyond the MVP spec.** Aggregation is expressed through **dashboard-level calcs** (`calcs.py`, keyed by dataset) — a chart references a calc by key instead of carrying its own `agg`/`value` (owner-approved; see architecture.md "Calcs"). A calc is one of three kinds: an **aggregate** (`count`/`sum`/`dcount`/`min`/`max`/`avg` over a row-level formula, with optional filters), a **derived** ratio over other calcs, or a **column** — a row-level formula over dataset columns that acts as a *dimension*, usable anywhere a column name goes (a chart's `x`/`column`, a filter, another calc). The kind is never written in the YAML: `agg` means aggregate, and a bare formula is sorted into derived vs column by what it references (`calcs._classify`). All three share a tiny `+ - * /` expression grammar with two functions, `str2dt(<column>, <pattern>)` and `to_number(<expr>)`, plus a `<prefix><0,.pattern><suffix>` format token. This includes per-calc row-level expressions (e.g. `price * qty`), derived ratios, and calculated columns — but stays an expression language: joins, SQL, `case`/string ops, and export remain out of scope, and `str2dt()` and `to_number()` are the only functions. `number`/`pie`/`bar` take one calc; `map` takes a `count`/`sum` calc (per-hex weight); `table` takes a **list** — `measures:` — grouped by its `columns:`, or reads at most the first 1000 raw rows when `measures` is empty. (Datasets are **Parquet in object storage** with efficient scans — a separate owner-approved extension.)

When in doubt: less code, fewer abstractions, hardcoded behavior, developer experience over architectural purity. The MVP is expected to be rewritten — if a solution feels generic, configurable, or extensible, it's probably wrong for this stage.

## UI style — minimalist, icon-first

Keep chrome **minimal**: prefer **icons over text** in buttons and actions (inline SVG, `stroke="currentColor"` so they follow the theme), with a `title`/`aria-label` carrying the meaning. Use as little visible text as possible — no verbose labels, no explanatory red banners; let a compact icon + a badge/count + a tooltip do the work. Concretely: **no section headings or group captions** where layout already groups things (a rule or spacing separates them; any name goes in a `title`); **states are icons**, not words (a check for current / in use, a spinner for building, a count badge for usage); a status line is the icon plus the one value that matters (`⟳ 1.2`, not "Building version 1.2…"); text appears only where it *is* the content (names, values, an error's own message). The portal gallery/dataset views are the reference (`portal.py` `_icon()`, the `.act` icon buttons, the trash-with-usage-count). New UI should match this.

## Code style

Code should read top-to-bottom like a story to someone who's never seen it: constants, helpers, then the class. Small functions; lift anything past one screen into a private `_helper` in the same file (no `utils.py`). Named locals over dense one-liners. Comments explain *why* (geometry, magic numbers tied to a template's `viewBox`, edge cases), not *what*. Delete dead code — git remembers. If a chart's `to_html` can't be skimmed in fifteen seconds, simplify before adding features.
